What's the Difference Between a Hotfix, Coldfix, Patch and Bug Fix?

Hotfixes and software patches refer to the same rapid fix of a defect. In some development teams, software patches refer to a service pack or group of multiple hotfixes deployed at the same time. Hotfixes and software patches are often referred to interchangeably, yet some consider a hotfix to have three differentiating characteristics: done on a live system, executed quickly, and applied without creating outages.

TermTimingPlanningRisk
HotfixApplied while the system is live ("hot")Unplanned, fast turnaroundHigher — bypasses the normal release process
ColdfixApplied with the system shut downPlanned, scheduled, announced to usersLower — full testing cycle before deployment
Software patchVaries — can bundle multiple hotfixes as a service packVaries by team conventionVaries with scope and bundling
Bug fixDeployed as part of a planned releaseCoded, tested, regression-tested, released on scheduleLowest — full QA process, including regression testing

A bug fix is a standard defect fix. Bug fixes are coded, tested, run through regression tests and then get deployed as part of a planned release. The majority of software development teams work from backlogs of previously entered defects or bugs. Developers also may create unit tests within the code to automatically test their bug fixes — often through test automation that runs alongside the manual verification a hotfix's compressed timeline doesn't always allow for.

Keys to Avoiding Hotfixes

The surest method of avoiding hotfixes is increasing the software testing scope, breadth and depth — building toward reliable software testing that reduces the pressure to patch after the fact. Plan for full regression testing against a Staging server that mirrors the Production server exactly. Additionally, do tests against all back-end messaging, database, API and other dependent connections, and use exploratory testing alongside scripted regression suites to surface the edge cases a checklist won't catch.

Test data must represent real production data at least in type and structure. Testing must encompass configuration settings or customizable settings. Test servers must run the same active connections that Production does rather than rely on simulated connection processing or simulated data loading. A QA professional runs a basic smoke test against all functionality before a hotfix reaches Staging, and ideally, that same discipline extends into everyday testing coverage rather than only kicking in once something's already broken.
